LEONED FRONTEND INTEGRATION - SESSION PROMOTION FLOW
====================================================

Purpose
-------
At the beginning of a new academic session, a School Admin can move all active
students to their next classes without losing their previous session's class,
results, attendance, fee, or enrollment history.



IMPORTANT DATA BEHAVIOR
-----------------------
- Student.classId represents only the student's current class.
- Historical class membership is now stored per academic session.
- The target classes used during promotion must belong to the school's current
  academic session.
- All source classes in one promotion request must belong to the same old session.
- All target classes in one promotion request must belong to the same new session.
- Promotion is atomic: either every valid mapping succeeds or no student is moved.


RECOMMENDED FRONTEND WORKFLOW
=============================

1. Create the new academic session.
2. Create the classes for the new session and provide academicSessionId.
3. Set the new academic session as current.
4. Load classes and group/filter them by academicSessionId.
5. Let the admin map each old-session class to one new-session class.
6. Send all class mappings to POST /api/promotion/promote.
7. Use POST /api/promotion/graduate for final-year classes that are graduating.
8. Display the returned promoted/graduate counts.


PROMOTION ENDPOINTS
===================

1. BULK PROMOTE STUDENTS
------------------------
Method: POST
Endpoint: /api/promotion/promote
Role: SchoolAdmin
Required header: School-Id

Request body:
{
  "mappings": [
    {
      "sourceClassId": "OLD_CLASS_UUID",
      "targetClassId": "NEW_CLASS_UUID"
    },
    {
      "sourceClassId": "ANOTHER_OLD_CLASS_UUID",
      "targetClassId": "ANOTHER_NEW_CLASS_UUID"
    }
  ]
}

Successful response data:
{
  "sourceAcademicSessionId": "OLD_SESSION_UUID",
  "targetAcademicSessionId": "NEW_SESSION_UUID",
  "totalPromoted": 75,
  "details": [
    {
      "sourceClassId": "OLD_CLASS_UUID",
      "sourceClassName": "JSS 1 A",
      "targetClassId": "NEW_CLASS_UUID",
      "targetClassName": "JSS 2 A",
      "promoted": 40
    }
  ]
}

Frontend requirements:
- A source class may appear only once in a request.
- Source and target class IDs cannot be the same.
- Show only old-session classes in the source selector.
- Show only current-session classes in the target selector.
- Submit all mappings together.
- Do not move students between sessions with PUT /api/student/:id.

Possible validation messages:
- Each source class can only appear once.
- Target class must be different from source class.
- One or more source or target classes were not found in this school.
- Class [name] must belong to an academic session before promotion.
- All source classes must belong to one session and all target classes to one session.
- Promotion must move students from an old session into a different session.
- The target classes must belong to the school's current academic session.
- A student is already enrolled in a different class in the target session.


2. GRADUATE A FINAL-YEAR CLASS
------------------------------
Method: POST
Endpoint: /api/promotion/graduate
Role: SchoolAdmin
Required header: School-Id

Request body:
{
  "classId": "FINAL_YEAR_CLASS_UUID"
}

Behavior:
- All active students in the class become Graduated.
- Their session enrollment is closed as Graduated.
- Their student login accounts are deactivated.
- Previous academic records remain available.


3. MARK A STUDENT AS LEFT
-------------------------
Method: PUT
Endpoint: /api/promotion/mark-left/:studentId
Role: SchoolAdmin
Required header: School-Id

Behavior:
- The student's current enrollment is closed as Left.
- The student's login account is deactivated.
- Previous academic records remain available.


4. GET STUDENT SESSION/CLASS HISTORY (NEW)
------------------------------------------
Method: GET
Endpoint: /api/promotion/student/:studentId/history
Role: SchoolAdmin
Required header: School-Id

Response data shape:
{
  "student": {
    "id": "STUDENT_UUID",
    "fullName": "Student Name",
    "admissionNumber": "ADM-001"
  },
  "enrollments": [
    {
      "id": "ENROLLMENT_UUID",
      "academicSessionId": "SESSION_UUID",
      "academicSessionName": "2025/2026",
      "classId": "CLASS_UUID",
      "className": "JSS 1 A",
      "promotedToClassId": "NEXT_CLASS_UUID",
      "promotedToClassName": "JSS 2 A",
      "status": "Promoted",
      "startedAt": "DATE_TIME",
      "endedAt": "DATE_TIME"
    }
  ]
}

Suggested UI:
- Add an "Academic History" or "Class History" section to student details.
- Display session, class, status, promotion destination, start date, and end date.


RELATED SESSION AND CLASS ENDPOINTS
===================================

5. CREATE A NEW ACADEMIC SESSION
--------------------------------
Method: POST
Endpoint: /api/academicsession

Existing endpoint; request format is unchanged.


6. SET THE NEW SESSION AS CURRENT
---------------------------------
Method: PUT
Endpoint: /api/academicsession/:id/current

This must be done before calling the promotion endpoint because promotion only
accepts target classes belonging to the current session.


7. CREATE A CLASS FOR THE NEW SESSION
-------------------------------------
Method: POST
Endpoint: /api/class

Relevant request fields:
{
  "name": "JSS 2",
  "arm": "A",
  "academicSessionId": "NEW_SESSION_UUID",
  "formTeacherId": "OPTIONAL_TEACHER_UUID"
}

academicSessionId is important for the promotion flow.


8. ATTACH AN OLD UNASSIGNED CLASS TO A SESSION
----------------------------------------------
Method: PUT
Endpoint: /api/class/:id

Request body:
{
  "academicSessionId": "SESSION_UUID"
}

Use this only when an existing class does not already have an academicSessionId.
A class already assigned to a session cannot be moved into another session.


9. DELETE CLASS - BEHAVIOR CHANGE
---------------------------------
Method: DELETE
Endpoint: /api/class/:id

The endpoint now rejects deletion when the class is referenced by student
enrollment history. The frontend should display the returned error message.


10. DELETE ACADEMIC SESSION - BEHAVIOR CHANGE
---------------------------------------------
Method: DELETE
Endpoint: /api/academicsession/:id

The endpoint now rejects deletion when the session contains historical student
or academic records. The frontend should display the returned error message.


STUDENT ENDPOINT CHANGES
========================

11. CREATE STUDENT
------------------
Method: POST
Endpoint: /api/student

Request format is unchanged. When classId points to a class with an academic
session, the backend automatically creates the student's session enrollment.


12. UPDATE STUDENT
------------------
Method: PUT
Endpoint: /api/student/:id

Behavior change:
- Corrections between classes in the same academic session remain allowed.
- Moving a student to a class in a different academic session is rejected.
- Use POST /api/promotion/promote for cross-session movement.

Possible error:
"Use the promotion flow to move a student into a class in a different academic session."


HISTORICAL REPORT ENDPOINTS
===========================

13. ENROLLMENT REPORT
---------------------
Method: GET
Endpoint: /api/report/enrollment

Useful query parameters:
- academicSessionId
- classId
- gender

Example:
/api/report/enrollment?academicSessionId=OLD_SESSION_UUID&classId=OLD_CLASS_UUID

When academicSessionId is supplied, class and status come from that historical
session enrollment rather than the student's current class.


14. ATTENDANCE REPORT
---------------------
Method: GET
Endpoint: /api/report/attendance

Required query parameters:
- classId
- termId

Optional query parameter:
- academicSessionId

Example:
/api/report/attendance?classId=OLD_CLASS_UUID&termId=OLD_TERM_UUID&academicSessionId=OLD_SESSION_UUID

Old-session attendance remains visible after students have been promoted.


15. FEE PAYMENT REPORT
----------------------
Method: GET
Endpoint: /api/report/feepayment

Required query parameter:
- termId

Example:
/api/report/feepayment?termId=OLD_TERM_UUID

The report now displays the student's class in that term's academic session.


16. STUDENT STATUS REPORT
-------------------------
Method: GET
Endpoint: /api/report/studentstatus

Useful query parameters:
- status: Active, Promoted, Graduated, or Left
- academicSessionId

Examples:
/api/report/studentstatus?status=Promoted
/api/report/studentstatus?status=Promoted&academicSessionId=OLD_SESSION_UUID

The response counts now include Promoted.


17. OUTSTANDING FEES REPORT
---------------------------
Method: GET
Endpoint: /api/report/outstandingfees

Required query parameter:
- termId

Example:
/api/report/outstandingfees?termId=OLD_TERM_UUID

Historical class names now come from the selected term's session enrollment.


18. EXPORT REPORT
-----------------
Method: GET
Endpoint: /api/report/export

The revised session-history behavior applies when type is one of:
- enrollment
- attendance
- feepayment
- studentstatus
- outstandingfees

Examples:
/api/report/export?type=enrollment&format=csv&academicSessionId=OLD_SESSION_UUID
/api/report/export?type=studentstatus&format=pdf&status=Promoted&academicSessionId=OLD_SESSION_UUID


UNCHANGED FEATURE AREAS
=======================

No endpoint changes were made to:
- Authentication
- Teachers
- Subjects
- Score entry
- Result calculation and publishing
- Payment processing
- Subscriptions
- Announcements
- Scheme of work
